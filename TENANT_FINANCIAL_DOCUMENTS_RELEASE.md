# Tenant-branded financial documents, editable line items and strict module visibility

**Status:** LIVE · Production commit `fa2a960d1e35aef850a449ffac2e584508fc495c`

## Decisions implemented

| Area | Decision |
|---|---|
| Document branding | Tenant-controlled company profile and custom logo, not hard-coded to the example quotation |
| Line items | Editable itemised rows on financial and order forms |
| Document coverage | The formal layout applies to all financial / order documents |
| Module visibility | Strict: a disabled module/resource disappears everywhere except Settings |

## What changed

### 1. Tenant-owned financial PDFs

- `src/lib/company.ts` stores the company profile in `organizations.config.company`. It includes display/legal name, registration and VAT numbers, address, contact details, banking details, quote introduction, payment terms, client-supplied materials, warranty/delivery, footer, prepared-by, deposit percentage and a validated PNG/JPEG data-URL logo. **No new Supabase migration was required.**
- Settings → **Document branding** edits the profile and uploads the tenant logo. `/api/[org]/meta` exposes the normalised profile to the running app and includes `Cache-Control: no-store`, so re-enabling or editing a module is reflected without a stale catalogue.
- `src/app/api/[org]/pdf/[resource]/[id]/route.ts` now builds a two-page, tenant-branded A4 document with `pdf-lib`: embedded logo or generated initials, legal identity, resolved client/supplier and project metadata, quotation/order heading, payment notice, navy item table, subtotal / deposit / balance / total, VAT and paid amounts, terms, materials, banking, warranty, notes, additional details, authorised signatory and a **Generated by MYLA** footer.
- Long legal names, registration/VAT numbers and contact details are confined to a dedicated left column, so they cannot collide with the document number and date. The example supplier **Shell Mark** is absent.
- `src/lib/financial.ts` supports structured `items` / `lineItems` arrays, JSON-array strings, legacy newline textarea lines and legacy fallback fields. Totals, tax, paid amounts, deposits and balances are derived from those lines; `editableLines` preserves blank editor rows.
- The same layout covers the 16 item-enabled registers: `estimates`, `bids`, `contracts`, `changeOrders`, `requisitions`, `purchaseOrders`, `goodsReceipts`, `payRuns`, `expenses`, `accounts`, `journals`, `budgets`, `arInvoices`, `paymentApps`, `apBills` and `payments`.

### 2. Editable itemised lines

- A new `LineItemsEditor` gives description, detail, quantity, unit price and live subtotal rows on quotation, invoice and the other item-enabled forms.
- `RecordForm`, `RecordDetail`, `ResourceTable` and `src/lib/records.ts` preserve structured rows and derive stored totals while keeping older records readable.
- The example-style quotation QA used three lines: `US$2,500`, `US$420` and `US$380`; a 10% markup produced `US$3,630`, a 70% deposit of `US$2,541` and a balance of `US$1,089`.

### 3. Strict module and resource visibility

- `src/lib/module-visibility.ts` requires **both** `config.modules` and `config.resources` to permit a resource. `hrefVisible` also filters `/m/<resource>` links and special pages.
- `src/lib/page-modules.ts` is wired into server layouts for the dashboard, documentation, library, wallets, reports, projects, project 360 and direct resource routes.
- `/meta` returns only readable modules/resources/definitions; `?scope=settings` deliberately keeps the full catalogue so administrators can re-enable sections.
- `/overview`, `/search`, `/integrity`, project 360, related records and PDF routes hide disabled resources. Settings is the only full-list exception; re-enabling a module restores its existing data and navigation.

## Known limitation

Strict module visibility is enforced in the application, API and server-page layers. Database RLS `app_can_read` still checks `config.resources` but not `config.modules`; no SQL module-gating migration was applied in this release. `RecordForm.initialValues` also still starts from all catalogue fields before the visibility layer filters what is shown.
