## Defects found and fixed

1. **PATCH wiped every field it did not receive.** Partial updates now merge stored JSON with incoming keys before validating.
2. **Broken cross-module links were accepted.** `validateRefs` checks each ref points to a live record of the correct resource in the same organisation.
3. **Seed data contained dangling employee/account references.** The generator draws employee refs from the real id list and account refs from the chart-of-accounts length.
4. **Disabling a module only blocked the list view.** Shared `guardResource`/`readGuard` guards now protect every record, file, comment, PDF, search, project-360, overview and wallet route.
5. **Sorting on data-backed columns only sorted the current page.** Rows are fetched, sorted, then paginated.
6. **Bulk delete over-reported its count.** It now returns the real `updateMany` count.
7. **Comments could be posted against arbitrary record ids.** The route verifies the record exists, is live, is org-scoped and matches the enabled resource.
8. **Generic CRUD could overwrite derived figures.** `readOnly` fields (`walletBalance`, `fundedAmount`, `remainingToFund`) are hidden from forms and pinned to their source module on create/update.
9. **External portal users could read the whole workspace.** `Membership.entityId` now pins client/subcontractor roles to their own client, projects and wallet; search, files, PDFs, meta, overview and project 360 all honour that scope.
10. **CSV import bypassed module and role checks.** It now uses the same `writeGuard` as record creation.
11. **Notification "mark all read" was admin-only.** Any signed-in user can now clear their own badge.
12. **The UI delete confirmation stayed open after success.** Closing it immediately prevents the overlay from blocking later navigation.
13. **Supabase RPCs return `409` for an already-reversed wallet entry.** The audit now accepts both `400` and `409` for that invariant, while still failing on a real double reversal.
14. **Live wallet allocation could be checked before the drawer refetched.** The browser audit now waits for the derived balance to fall instead of assuming a fixed 700 ms refresh.
15. **A loading skeleton row looked like a clickable client row.** The linked-record browser check waits for a populated `<tbody>` row and clicks a data cell, avoiding the checkbox/status controls that stop propagation.
16. **`/api/[org]/meta` reported an empty team list on Supabase.** `memberships.user_id` references `auth.users`, not `public.profiles`, so PostgREST could not embed `profiles(...)`. The route now resolves visible profiles in a second RLS-scoped query and joins them in memory; Settings → Users & roles and the onboarding team checks see real members again. This also exposes 13 legitimate role-fixture cleanup checks, raising the live API total from 1198 to 1211.
17. **One stalled chunked Supabase response could hold the whole HTTP audit for minutes.** The audit client now uses `Connection: close`, a short read timeout, a hard 60-second `SIGALRM` deadline and one retry for idempotent GETs; a transient stalled wallet read no longer becomes a false failure.

## Scope decision — essentials first

New workspaces start with **13 connected essentials**:

`dashboard · company · crm · pipeline · estimating · projects · contracts · documents · finance · wallets · hr · time · reports`

That is one commercial chain — clients → leads → estimates & bids → projects → contracts → invoices → payments → client wallets — plus people and reporting. Type, size, qualifiers and explicit add-ons layer on more modules on a ramp (MICRO 13 → SMALL 13 → MID 17 → LARGE 29 → ENTERPRISE 30, mixed group 33).

- Onboarding step 5 labels core modules, lists every optional add-on, and offers **Enable all** / **Reset to essentials**.
- Settings → Modules has one-click **Essentials (13)** / **All modules** focus switching; individual toggles still work.
- The seeded demo organisation intentionally keeps all 34 modules enabled as the enterprise reference workspace (and so the audit can exercise all 49 resources).

## Client wallets

One prepaid `Wallet` per client, an append-only `WalletTransaction` ledger and integer cents (no float drift). Owners/admins/finance managers top up; those roles and client-portal users allocate to a project that belongs to the same client. Every movement mirrors into the client register (`walletBalance`), the project register (`fundedAmount`, `remainingToFund`), dashboard KPIs and project 360. Corrections are `REVERSAL` entries — ledger rows can never be edited or deleted (PATCH/DELETE → 405). Idempotency keys prevent double submissions; balances are reconciled by `/api/[org]/integrity`.

## Role-level access

A single `ROLE_RULES` matrix in `src/lib/catalog.ts` drives every API guard, the sidebar, quick-create, forms, settings and the audit suite. It covers 14 roles with per-resource read/write denylists, delete rights, 16 capabilities and row-level scoping for external users. Settings → Users & roles lets owners/admins change a member's role, pin a portal user to a client, remove members and see the full matrix; owner escalation and removal of the last owner are blocked server-side.
